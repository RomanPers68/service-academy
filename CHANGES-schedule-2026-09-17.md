# График и виброотдача — правки от 17.09.2026

Правки точечные. Затронуты три файла: `ui/schedule.jsx`, `ui/css.js`,
`lib/utils.js`. Логика генератора, формат данных и обмен с сервером
не тронуты — расстановка, замки, факт часов и зарплата считаются как раньше.

---

## 1. `ui/schedule.jsx` — «ПОКРЫТИЕ 0 %» при полной таблице (баг)

Значение покрытия писалось в `covTarget.current` в теле вида менеджера,
то есть **после** раннего выхода `if (state === "load") return`. На монтировании
эффект анимации стартовал на пустых данных (0 → 0), а когда график приезжал
с сервера, перезапускать эффект было нечем: в зависимостях стояли только
`genKey`, `mkey`, `weekIdx`. Цифра навсегда оставалась нулём (на записи экрана
видно `ПОКРЫТИЕ 0%` и `8%` при живых 1/1, 5/5 в таблице).

Теперь покрытие считается в `useMemo` **до** эффекта и попадает в его
зависимости, поэтому цифра догоняет реальность и после загрузки, и после
каждой правки. Ref `covTarget` стал не нужен и удалён.

## 2. `ui/schedule.jsx` — палитра смен вместо перебора по кругу

Тап по клетке перебирал смены циклом `["", ...shifts]`: при трёх сменах
поставить третью — три касания, стереть — четыре, и каждое промежуточное
касание закрепляло клетку замком.

Теперь тап открывает нижний лист с выбором: цвет, буква, название, время
и часы каждой смены плюс отдельная строка «Выходной». Для занятой клетки
там же кнопки «Кто вместо?» и «Факт часов» — те же экраны, что и в режимах,
но без переключения режима. Ставит смену новая функция `setCell(id, d, k)`.

Режимы «Правка · Кто вместо? · Обмен · Факт часов» оставлены как были:
их поведение не менялось, «Обмен» по-прежнему требует двух касаний.

## 3. `ui/schedule.jsx` — ручная правка попала в «Отменить»

`snapUndo()` вызывался только для генерации, обмена, очистки и снятия замков.
Самое частое действие — обычный тап по клетке — страховкой не покрывалось.
Теперь `setCell` снимает снимок перед изменением, и «↩» возвращает последнюю
поставленную смену.

## 4. `ui/schedule.jsx` + `ui/css.js` — имена в одну строку

В колонке шириной 100 px «Каирлинова Анастасия», «Никифоров Никита»,
«Мирослава Олехнович» переносились на вторую строку и удваивали высоту ряда.
На 19 сотрудниках это лишний экран прокрутки.

Добавлен модульный помощник `shortName()` → «Каирлинова А.». Полное имя
осталось в `title` ячейки и во всех остальных местах (аналитика, «Сегодня»,
экспорт картинкой, настройки) — сокращена только сетка. Колонка ужата
до 92 px с `max-width`, добавлены `nowrap` и многоточие.

## 5. `ui/schedule.jsx` — текущий месяц открывается на текущей неделе

`weekIdx` стартовал с `null` («весь месяц»), то есть 30 колонок по 26 px
внутри страницы, которая листается вниз. Новый эффект при открытии текущего
месяца выбирает неделю, в которую попадает сегодня; для других месяцев
остаётся «весь месяц». Ручной выбор не перебивается — эффект срабатывает
только на смену месяца.

## 6. `ui/schedule.jsx` — одна легенда вместо двух

Палитра печаталась дважды: сокращённая над таблицей и полная под ней.
Нижняя удалена, время смен (`11:00–24:00`) перенесено в верхнюю.

## 7. `ui/schedule.jsx` — вид сотрудника: «ближайшая смена» наверх

Строка стояла девятым блоком — после часов, заработка, прошлого месяца,
«+2 смены», достижений, обмена сменами и чек-листа. Ради неё график
и открывают. Поднята сразу под имя и увеличена: день, название смены,
время, часы и старший смены с кнопкой звонка.

## 8. `ui/schedule.jsx` — вид сотрудника: список дней

- Нерабочие дни сжаты (меньше отступы, шрифт даты 14 вместо 17, прозрачность 0.75) —
  смены складываются в различимый ритм вместо тридцати одинаковых строк.
- Подпись выходного была случайной из трёх (`["Выходной", "Отдыхай ✦", "Твой день"][d % 3]`);
  одно состояние — одно слово, «Выходной».
- Пустая строка времени под выходным больше не рисуется (занимала высоту зря).

## 9. `ui/schedule.jsx` — настройки: подпись перед нумерованными разделами

Над разделами 1–6 стоят две карточки-помощника без номера, и список выглядел так,
будто нумерация начинается с третьего пункта. Добавлена строка «шесть шагов настройки».

## 10. `lib/utils.js` — виброотдача в APK (баг)

`vibrate()` проверял `window.Telegram?.WebApp?.HapticFeedback` и, если объект есть,
уходил в ветку Telegram. Но `telegram-web-app.js` подключён в `index.html`
безусловно — он грузится и в APK, и в обычном браузере, и всё равно создаёт
`WebApp.HapticFeedback`. Проверка проходила **всегда**, вызывалась пустышка,
и до `navigator.vibrate` управление не доходило. В Telegram вибрация работала,
в установленном приложении — нет.

Добавлена функция `inTelegram()`: настоящий клиент определяется по непустой
`initData` либо по `platform`, отличной от `"unknown"`. Вне Telegram теперь
честно используется Web Vibration API.

### Важно: одной правки кода может не хватить

`navigator.vibrate()` внутри TWA работает только если в манифесте Android-приложения
объявлено разрешение:

```xml
<uses-permission android:name="android.permission.VIBRATE" />
```

PWABuilder этого разрешения по умолчанию не добавляет. Если после обновления сайта
отдачи в APK всё ещё нет — дело в манифесте, и чинится это при пересборке пакета
(в PWABuilder → All Settings включить исходный код и добавить строку, либо собрать
через Bubblewrap). Проверить просто: та же сборка в обычном Chrome на том же
телефоне должна вибрировать — если вибрирует в Chrome, но молчит в приложении,
причина именно в разрешении.

Отдельно проверь в системных настройках телефона, что включена «вибрация при
нажатии» и телефон не в режиме энергосбережения — Chrome глушит вибрацию в обоих случаях.

## Что НЕ делалось (осознанно)

- **Режимы не убраны.** Предлагал свести «Правка · Кто вместо? · Обмен · Факт часов»
  в одно меню у клетки. Палитра закрывает частый случай, но полный демонтаж режимов
  задевает обмен (два касания) и требует проверки на живых данных — без сборки
  и прогона тестов это риск.
- **Замечания не сделаны кликабельными.** Чтобы тап по строке прыгал к нужному дню,
  `audit()` должен возвращать объекты `{ day, staffId, text }` вместо строк,
  а его результат используется ещё и в экспорте картинкой и в подсказках генератора.
  Это отдельная правка, не «заодно».
- **Переработки.** Каирлинова 254/195, Старченко 221/195, Марк Финке 201/195 —
  это +30…+60 часов сверх нормы, и половина полосок в таблице красная. Когда
  красным горит половина команды, красный перестаёт быть сигналом. Но это вопрос
  к настройкам норм или к генератору, а не к интерфейсу, — интерфейс показывает
  честно.

## Дополнение: «морозный лёд» в палитре смен

Новый лист выбора смены изначально унаследовал плоский стиль модалки
«Кто вместо?» (сплошная заливка + золотая рамка). Переведён на общую
рецептуру карточек графика — в обеих темах:

- полупрозрачное стекло вместо сплошного фона;
- свечение изморози изнутри (`inset 0 0 …`);
- блик по верхней кромке (`inset 0 1px 0`) и более светлый `border-top`;
- мягкая тень наружу снизу, чтобы лист «лежал» на экране.

Светлая тема получает тёплое молочное стекло, тёмная — тот же приём
на тёмном янтаре. Выбранная строка подсвечивается золотом, не теряя стекла.

# Генератор смен — правки от 17.09.2026 (вторая серия)

Файлы: `lib/schedule-gen.js`, `ui/schedule.jsx`. Жёсткие правила (отпуск,
выходные, цикл 2/2, отдых, «подряд», недельные квоты) не тронуты — весь
`canPlace` как был. Менялись только приоритеты раздачи и оценка расстановки.

## 11. Балансировка по доле СВОЕЙ нормы, а не по числу смен (главное)

Было, в жадном проходе:

```js
if (cnt[a.id] !== cnt[b.id]) return cnt[a.id] - cnt[b.id];   // у кого меньше смен
```

При одинаковых нормах это честно. Но как только в команде появляется
полставочник (студент с нормой 100 против 195 у полной ставки), «равное число
смен» означает для него двойную переработку. Теперь сравнивается доля от
личной нормы с учётом длины предлагаемой смены, с допуском 2 %
(≈4 ч на ставке 195) — внутри допуска решают прежние ключи и джиттер.

Замер на стенде: 6 полных ставок (195 ч) + 3 полставки (100 ч),
потребность 4 чел/день и 5 в пик, среднее по 5 посевам.

|                            |   ДО  | ПОСЛЕ |
|----------------------------|------:|------:|
| загрузка полных ставок     |  96 % | 113 % |
| загрузка полставочников    | 182 % | 113 % |
| разрыв между крайними      |  89 % |  13 % |
| переработка полставок      | 246 ч |  38 ч |
| незакрытых дыр             |   0   |   0   |

Полставочники работали 182 часа при норме 100. Теперь нагрузка легла
пропорционально, покрытие не пострадало.

## 12. Переработка штрафуется в счёте

Оценка учитывала только недоработку (`Math.max(0, norm - hours)`). Перебор
часов не стоил ничего, и раздавать его было выгодно: лишний час одному
уменьшал недобор у другого. Теперь час переработки дороже часа недоработки,
вес правится через `rules.overWeight` (по умолчанию 2.5).

Честно про эффект: **сам по себе этот штраф почти ничего не меняет.** Он
выбирает лучший из 24 прогонов, а если все прогоны одинаково перегружены —
выбирать не из чего. Реально работает правка №11, а штраф — страховка
на случай, когда у мультистарта есть выбор.

## 13. Справедливость пиков считалась неверно

```js
sc += (Math.max(...peaks, 0) - Math.min(...peaks, 0)) * 0.5;
```

Минимум брался по всем, включая отпускников с нулём смен: у человека в отпуске
весь месяц `peaks = 0`, и разброс превращался в «максимум минус ноль» — метрика
ничего не мерила. Теперь считаются только реально работавшие (порог 4 смены,
тот же, что у справедливости типов смен).

## 14. Генератор стал воспроизводимым

Внутри стоял `const seed = (Date.now() & 0xffff)` — каждое нажатие «Заполнить»
давало другой график. Менеджер жал дважды, видел разные расстановки и переставал
понимать, думает машина или бросает кости.

Теперь посев приходит снаружи, из месяца: `(Y*12 + M)*7919 + mix*104729`.
Один месяц с теми же настройками — один и тот же результат. Другой вариант
запрашивается явно: в «Ещё» появилась кнопка **«Перемешать»** (сдвигает посев,
дальше обычное «Заполнить черновик»).

Проверено: при запасе людей (12 человек на потребность 5–6) восемь посевов дают
семь разных графиков. При тесном штате все посевы сходятся в один — и это
правильный ответ: другого хорошего расклада просто нет.

## Что дальше, если захочешь

Самое крупное из оставшегося — **локальный поиск после ремонта**. Сейчас
`repair()` чинит только дыры, хотя `score(pm)` и `canPlace` уже написаны:
цикл «возьми случайную смену, попробуй передать другому или переставить на

локальный поиск на порядок эффективнее той же ценой.

## 15. Уволенные получали смены (баг, вероятно заметный)

Метка `till` — последний рабочий месяц человека. Интерфейс её учитывал:

```js
const staff = staffAll.filter(q => !q.till || mkey <= q.till);   // ui/schedule.jsx
```

Но в генератор уходил **сырой `cfg`**, а внутри стояло просто `cfg.staff || []`.
Уволенный в июле продолжал получать смены в сентябре.

Последствие хуже, чем кажется. В таблице его строки нет — она рисуется по
отфильтрованному списку. Зато слот дня он занимал: генератор считал потребность
закрытой и шёл дальше, а на экране день выглядел недобранным, и объяснить эту
дыру было нечем. Часть «не хватает 14 смен» могла быть именно этим.

Проверено на стенде: до правки уволенный в июле получал 20 смен в сентябре,
после — ноль.

Фильтр перенесён внутрь генератора (он и так знает `mkey`), поэтому чинятся
все пять мест вызова разом, а не только «Заполнить черновик».

### Заодно проверено, что остальные ограничения работают

Один месяц, восемь человек, все ограничения сразу — все проверки прошли:

- уволенный не получил ни одной смены;
- отпускник свободен 10–20 и при этом работает вне отпуска;
- постоянный выходной по воскресеньям соблюдён;
- разовые выходные конкретными датами (5 и 6) соблюдены;
- «не смогу выйти» (12, 13, 14) соблюдено;
- дыр при этом ноль.

Все пять — жёсткие правила внутри `canPlace`: ни жадный проход, ни ремонт
их не обходят. Пожелания о выходных (`wishes`) — мягкие: уважаются, пока не
ценой дыры в зале.

# Экран пожеланий сотрудника — 17.09.2026 (третья серия)

Файл: `ui/schedule.jsx`. Серверная часть и формат данных не тронуты — всё
работает через существующий `setWish(staffId, d, on, kind)`, те же квоты,
та же синхронизация, тот же `hardCapacity`.

## 16. Пожелания за одно действие вместо тридцати раскрытий

Кнопки «Попросить выходной» и «Не смогу выйти» существовали и раньше, но
лежали **внутри раскрытого дня**. Чтобы отметить отпуск с 10 по 20, человек
делал двадцать два касания: одиннадцать раскрытий плюс одиннадцать нажатий.
Проще было написать менеджеру в мессенджер — так все и делали, а менеджер
вбивал это руками. Вот где уходило время, а не в генераторе.

Добавлена карточка «Мои пожелания» над списком дней:

- **весь месяц одной сеткой**, 7 колонок, с понедельника, выровнено по дням недели;
- состояние каждого дня читается цветом: свободен, прошу выходной (золото),
  не смогу (красный), уже смена, отпуск, постоянный выходной, прошедший день;
- **тап по дню** открывает лист с выбором — просьба, «не смогу», убрать отметку
  (тот же «морозный лёд», что у палитры менеджера, в обеих темах);
- **«Отметить период»** — два тапа на первый и последний день, дальше один выбор
  на весь диапазон;
- сверху счётчик: сколько просьб и сколько «не смогу» уже отмечено.

Отметка периода идёт циклом через тот же `setWish` и честно отчитывается:
дни со сменой, отпуском или постоянным выходным пропускаются, а если на день
кончилась квота «не смогу» — это попадает в итог отдельной цифрой
(«отмечено дней: 8 · на 3 — мест уже нет»). Тихо проглотить часть диапазона
было бы хуже всего.

## 17. Срок приёма пожеланий

В «Правилах смен» появилось поле «пожелания принимаем до числа» (0 — без срока).
Сотрудник видит его на своём экране: «Принимаем до 25 числа — после график
собирается». После этой даты сетка текущего месяца закрывается для правок
и объясняет почему.

Это же поле — опора для будущей автосборки: собирать месяц имеет смысл
после закрытия приёма, а не по пустым пожеланиям.

## 18. У сотрудника не рисовалась строка состояния

`setMsg()` вызывался и в ветке сотрудника, но сам `msg` выводился только в виде
менеджера. Любой ответ системы сотруднику уходил в пустоту. Добавлена строка
состояния — без неё отчёт об отметке периода был бы невидим.

# Почему настройки не сохранялись и автозаполнение молчало

Две причины, обе в коде, обе объясняют симптомы. Файл: `ui/schedule.jsx`.

## 22. Слияние настроек с умолчаниями было поверхностным

```js
setCfg(v ? { ...DEFAULT_CONFIG, ...v.config } : { ...DEFAULT_CONFIG });
```

Спред поверхностный: если в сохранённой настройке есть ключ `rules`, он
заменяет `DEFAULT_CONFIG.rules` **целиком**. Значит любое поле, добавленное
в умолчания позже, отсутствует у всех, кто настраивался раньше.

Прямое следствие: `cfg.rules.autoFill` приходил с сервера как `undefined`,
и эффект автосборки выходил на первой же проверке — **автозаполнение не могло
сработать в принципе**. С `wishDeadline` то же самое: срок приёма пожеланий
не показывался никому.

Добавлена `mergeCfg()` — сливает вложенные объекты (`rules`, `need`, `split`,
`posRules`) по ключам. Применена в обоих местах загрузки: с сервера и из
офлайн-копии.

Проверено на настройке, сохранённой до появления новых полей:

```
✓ новое поле autoFill появилось
✓ новое поле wishDeadline появилось
✓ сохранённое peakDows НЕ затёрто умолчанием
✓ сохранённое maxRow НЕ затёрто
✓ сохранённый need уровня 1 сохранён
✓ недостающий уровень 3 взят из умолчаний
✓ staff не тронут
```

## 23. Отложенное сохранение настроек терялось

```js
saveTimer.current = setTimeout(() => saveCfg(next), 900);
```

Правка применялась мгновенно, а на сервер уходила через 900 мс. Паузу никто
не дожидался: закрыл приложение или переключил месяц в эти секунды — таймер
умирал вместе с компонентом, и настройка пропадала бесследно. Так и выглядело
«настройки не сохраняются»: переключил, вышел, вернулся — всё как было.

Отдельно: переключение месяца вызывает `load()`, а тот делает `setCfg()`
ответом сервера. Свежая правка визуально откатывалась ещё до того, как
успевала уйти.

Теперь несохранённое лежит в `pendingCfg` и дописывается принудительно:

- при уходе со страницы (`pagehide`);
- при сворачивании приложения (`visibilitychange` → hidden);
- при размонтировании компонента;
- перед любой перезагрузкой месяца.

## Про автозаполнение: условия остались строгими

Даже после починки автосборка срабатывает только если месяц **полностью
пуст**. Для текущего месяца, где смены уже расставлены, она не сработает
никогда — и это задумано, чтобы автоматика не спорила с человеком.
Если ожидается другое поведение (например, дозаполнять дыры в уже начатом
месяце), это отдельное решение и отдельная правка.

## Что осталось негибким: отпуск

## 30. Мёртвые колонки: числа, которые никогда не применяются

# Два уровня загрузки вместо трёх — 18.09.2026 (десятая серия)

## 34. «Высокий» и «пик» слиты в один уровень

Замечание владельца: два названия для одного смысла — «людей нужно больше
обычного» — путают того, кто настраивает. И это подтверждается его же данными:
Официант 5/5/6, Раннер 1/1/2, остальные 1/1/1 и 2/2/2. **«Высокий» нигде
не отличается от «обычного»** — уровень есть, разницы нет.

Теперь по умолчанию уровня два: **обычный** и **пиковый**. Третий включается
переключателем в «Правилах смен» — для тех, кому нужна разница между
«четверг чуть плотнее» и «суббота забита».

### Ничего не пропадёт у тех, кто третьим пользуется

Число уровней **определяется по данным**, а не навязывается: если хотя бы
у одной должности число в «высоком» отличается и от обычного, и от пика —
третий уровень включается сам. Явный выбор в настройках перебивает
автоопределение в обе стороны.

Я чуть не сломал это сам: сначала добавил `levels: 2` в `DEFAULT_CONFIG.rules`,
а после глубокого слияния (правка №22) умолчание пришло бы **всем**, включая
тех, у кого третий уровень настроен. Поле из умолчаний убрано, работает
автоопределение.

### Что поменялось в коде

- `LVLS` — один список уровней на все экраны: потребность, разбивка по сменам,
  расшифровка дней, сводки разделов. Раньше `[1,2,3]` было зашито в пяти местах,
  и они могли разъехаться.
- `lvlOf` не возвращает 2 при двух уровнях, а день, вручную помеченный
  «высоким», читается как пик — иначе он попал бы на уровень, которого
  на экране нет.
- Переход на два уровня гасит «высокие дни»: иначе день остался бы на
  мёртвом уровне, и задать для него потребность было бы нечем.
- Правка потребности «обычного» при двух уровнях синхронно пишет и в
  «высокий» — чтобы данные не разъехались, если третий уровень включат позже.
- «Пик» переименован в «пиковый» — согласовано с расшифровкой дней.

### Проверка на восьми сценариях

```
✓ у владельца определяется ДВА уровня
✓ где «высокий» отличается — определяется ТРИ
✓ явные два перебивают автоопределение
✓ явные три перебивают автоопределение
✓ при двух уровнях уровень 2 не встречается
✓ пиковый день всё ещё определяется
✓ при трёх уровнях «высокий» возвращается
✓ праздник остаётся пиком
```

# Справедливость типов смен — 18.09.2026 (одиннадцатая серия)

## 35. Одному человеку доставалось 3–4 утра подряд

Жалоба владельца. На ровных данных не воспроизвелась: восемь официантов без
ограничений дают максимум две одинаковые смены подряд и перекос по типам 9 %.
Воспроизвелась, когда в стенд добавили реальную жизнь — постоянные выходные
по дням недели, отпуск, «не смогу выйти»:

```
самая длинная серия одной смены подряд: 4
случаев «3 подряд одинаковых» за месяц:  5.4
перекос по типам смен (доля, среднее):   23%
```

Причина в том, что **справедливость считалась только по сумме за месяц**, а на
вчерашний день не смотрел никто. Когда пул кандидатов тонкий, слот раз за разом
достаётся одному и тому же человеку. Для денег это ощутимо: утро 6 ч против
дня 13 ч — три утра подряд стоят вдвое дешевле трёх дней.

### Что сделано

1. **Ключ сортировки помнит вчера.** При раздаче слота считается, сколько дней
   подряд человек уже выходит именно в эту смену, и слот уходит тому, у кого
   серия короче.
2. **Счёт мерил только самый поздний тип смены** («никто не живёт в вечерах»).
   Но перекос по утрам бьёт по деньгам ровно так же. Теперь спред доли
   считается по каждому авто-типу внутри позиции.
3. **Штраф за серии в счёте**: третья одинаковая подряд и каждая следующая.
   Ключ сортировки гасит серии при раздаче, счёт добивает на мультистарте.

### Результат на том же стенде

|                                | ДО  | ПОСЛЕ |
|--------------------------------|----:|------:|
| самая длинная серия            |  4  |   1   |
| случаев «3 подряд» за месяц    | 5.4 |   0   |
| перекос по типам смен          | 23% |  18%  |
| незакрытых дыр                 |  0  |   0   |

Покрытие не пострадало, разброс часов не изменился (он держится
полставочником и отпускником — так и должно быть).

### Поправка: основная смена из правила исключена

Первая версия чередовала **все** типы смен, включая «День» — и это было
неверно. День 11:00–24:00 это полная смена, обычный рабочий день; ходить
в неё несколько дней подряд нормально, и заставлять человека прыгать
с полного дня на утро и обратно — не справедливость, а вред.

Чередуются только короткие смены — утро и вечер: они отличаются и часами
(6 и 7 против 13), и временем начала. Основная смена (`cfg.dayShift`)
выведена и из ключа сортировки, и из штрафа в счёте.

### Результат на том же стенде

|                                  | ДО  | ПОСЛЕ |
|----------------------------------|----:|------:|
| подряд утро/вечер одного типа    |  4  |   2   |
| случаев «3 подряд» за месяц      | 5.4 |   0   |
| подряд полных дней               |  4  |   4   |
| перекос по типам смен            | 23% |  22%  |
| незакрытых дыр                   |  0  |   0   |

Полные дни идут подряд как и раньше — до `maxRow`, это норма, а не перекос.

### Остаточный перекос структурный

Разброс по утрам (у кого-то 2, у кого-то 5) усилением веса справедливости
почти не лечится: пробовал 3 → 12 → 40, перекос сдвинулся 22 % → 22 % → 20 %,
а вес 40 начинает спорить со штрафом за нарушенные пожелания. Причина не в
алгоритме, а в доступности: у людей разные постоянные выходные, отпуска и
«не смогу», и в конкретный день на утро физически некому больше выйти.
Оставлен осторожный вес 3.

## 36. Две дыры в правиле чередования (правка защитная, не доказанная)

Правило «не давать третью одинаковую смену подряд» я добавил только в
основной ключ сортировки. Мимо него шли два пути назначения:

1. **Запасной путь** в жадном проходе: когда основная смена не заходит,
   перебираются остальные типы, и кандидат выбирался сортировкой
   «пожелание → недобор до нормы → джиттер». Ни серии, ни числа таких
   смен там не было.
2. **Ремонт дыр** — выбирал человека через `staff.find(...)`, то есть
   **первого подходящего по порядку в списке**. Никакой справедливости
   вообще: при повторных прогонах слот раз за разом уходил одному и тому же.

Добавлен общий помощник `pickFair(pm, list, d, k)` — очередь по правилам:
пожелание → длина серии этой смены → сколько таких смен уже набрано →
недобор до нормы. Применён в обоих путях. Полный день (`baseK`) из счёта
серий исключён, как и в основном проходе.

**Честно о результате.** A/B на тесном стенде (7 официантов, потребность 4,
отпуск, постоянные выходные, «не смогу», 31 день, 5 посевов) дал одинаковые
числа до и после правки: максимум 2 подряд, ноль случаев «три подряд», ноль
дыр. То есть дыры в логике настоящие, но воспроизвести их выстрел на
доступных данных не удалось. Правка оставлена как защитная: путь без правил —
это мина, даже если она сегодня не сработала.

## 37. Найдена настоящая причина серий: порядок ключей

Владелец подтвердил, что жалоба была на **актуальной сборке** — значит
правка №35 проблему не закрыла. И действительно: я сам поставил ключи
в неверном порядке.

```js
if (!sl.flex) {                    // утро/вечер — слот без flex
  if (ea !== eb) return ea - eb;   // у кого МЕНЬШЕ таких смен за месяц
}
if (sl.k !== baseK) {              // и только ПОТОМ — серия
  if (ra !== rb) return ra - rb;
}
```

Справедливость по сумме за месяц решала **раньше** проверки серии. Человек,
вышедший из отпуска с нулём утр, выигрывает этот ключ каждый день подряд —
пока не догонит коллег. До проверки серии дело просто не доходило.

Воспроизведено точно на сценарии владельца (Толкачева, отпуск 1–20 октября,
семь официантов, потребность 5, разбивка 1У+3Д+1В):

```
ДО:     ····················ДДДД·ДВВВ·В     ← три вечера подряд
ПОСЛЕ:  ····················ДДДД·ДВУВ·В     ← вечер, утро, вечер
```

| на сценарии с отпуском         | ДО | ПОСЛЕ |
|--------------------------------|---:|------:|
| самая длинная серия утра/вечера|  3 |   2   |
| случаев «3 подряд» за 5 посевов|  5 |   0   |

Проверка серии поднята **выше** ключа справедливости по сумме. Догонять по
числу смен человек теперь будет через день, а не подряд.

Регрессия: тесный стенд, стенд с ограничениями, отпуска по месяцам,
заполнение по должностям, девять проверок ограничений и восемь утверждений
из `tests/schedule-gen.test.js` — всё прежнее, дыр ноль.

### Чему это меня научило

Правка №35 была проверена на стендах, где все накапливали смены равномерно —
и потому выглядела рабочей. Случай «вернулся из отпуска с нулём» такие стенды
не покрывали. Замер без сценария, ломающего гипотезу, доказывает только то,
что код не падает.
